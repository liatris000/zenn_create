# 記事スタイルガイド

zenn.dev/liatris に公開する記事の文体・構成の方針を定義する。

**最終更新**: 2026-11-07
**対象**: Claude Code が生成する記事 + Liatris が編集する記事
**目的**: AI 記事のテンプレ感を脱却し、Liatris らしさが出る記事にする

## このガイドの位置づけ

`zenn_create` の Day 1〜3 で生成される記事は、本ガイドに従って書かれる。
本ガイドは [`.claude/skills/article-writing/SKILL.md`](../.claude/skills/article-writing/SKILL.md) から自動参照される。

## 何を最適化するか

優先順位順:

1. **読者への貢献** ─ 読者が持ち帰れるもの(手順・数字・判断の基準)がある。読者には自分も含む。後から自分が読み返して役に立つ記事は、読者への価値がある
2. **転職市場露出** ─ データアナリストとしてのキャリア軸が見える
3. **キャッチアップ価値の自己開示** ─ Liatris が何を学んで何を考えたかが分かる
4. **AI らしさからの距離** ─ テンプレ的構成・定型表現を避ける

2026-11-07 に、読者への貢献を 3 番目から 1 番目にした(2026-11 の振り返りで、週 1 本の記事が読まれなかった理由の 1 つが、読者が最後になっていたことだった)。

## 何を最適化しないか

- 短期的な PV / バズを狙った煽り(題材の早さは別。速報・初見は先に出す)
- SEO のための機械的な見出し量産
- 全方位網羅(範囲を絞る方が深く書ける)
- 「綺麗にまとまっている」こと(綺麗さ ≒ AI 臭)

## やらないこと(禁止リスト)

### 表現レベルの禁止

#### リード文のテンプレ表現

- ❌「〜と感じたことはないでしょうか」
- ❌「〜で悩んでいる方も多いのではないでしょうか」
- ❌「結論から言うと、〜」
- ❌「今回は〜について解説します」

リード文は **題材固有の問題提起** から書き始める。

例(良い): 「Claude Code の Hooks を業務スクリプトに組み込んでみたら、想定外に dbt 開発フローが楽になった。」
例(悪い): 「Claude Code Hooks を使って開発フローを自動化したいと感じたことはないでしょうか。今回はその方法を解説します。」

#### 構成のテンプレ

- ❌「良かった点 / 惜しかった点 / 業務での活用イメージ」を毎記事に置かない
- ❌「まとめ」セクションを毎記事に置かない(自然に終われるなら不要)
- ❌「こんな方に試してほしいです」のリストで記事を締めない

これらは「AI が記事を書いた」と即座に判別される構造。題材ごとに構成を変える。

#### 文末のテンプレ

- ❌「いかがでしたか」
- ❌「ぜひ試してみてください」
- ❌「参考になれば幸いです」

これらは何も伝えていない決まり文句。題材固有の余韻を残す。

### 内容レベルの禁止

#### 業務コンテクストの露出

- ❌ 業務文脈・関係者・取引先・パートナー・提携先を出さない
- ❌ 実勤務先 / 受託先 / 関係する事業を動機として書かない(「〇〇で困っていた」「〇〇で作った」「〇〇で議論されている」の形)
- **どの固有名詞が NG かの正本は `business-profile/policies/disclosure-rules.md`**。会社ごとに ❌ / ✅ の具体例が載っている。このリポジトリは Public なので実名はそちらに置き、ここには書かない

#### 本名の露出

- ❌ 記事本文内に「平野翔斗」と書かない
- ✅ プロフィール表示は本名 OK

#### フィクションの数値

- ❌「クエリ実行時間が 1.5 秒から 0.3 秒に改善」のような未確認の数値を書かない
- ✅ 実際に計測した結果のみ書く

## やること(必須要素)

### 必須セクション(順序自由)

各記事に以下を入れる。順序や重み付けは題材に応じて変える。

#### A. 測って決める視点(必須)

**目的**: キャリア軸(データで判断する人であること)が記事の中で見えるようにする。

データ分析の視点は、たとえではなく判断に使う。記事のどこかで「何を測ったか」と
「その数字で何を決めたか(決めるか)」を書く。独立した段落や見出しにせず、判断を
書いている箇所に混ぜる。

例(判断に使っている):

- 「375 / 768 / 1280px の 3 点確認は、連続した幅を 3 つの標本で代表させているだけだった。掃引して境界を実測したら 800〜912px で崩れていた。」
- 「経路ごとの件数を出しているので、`reply_failed_then_push` が 0 でなければ閾値が攻めすぎだと判断できる。」

例(たとえで終わっている。書かない):

- ❌「OCR 結果を構造化する発想は、SQL の集計前処理と同じ構造をしている。」
- ❌「この仕組みはデータ基盤の row-level security と相似だ。」

ただし以下は避ける:

- ❌「データアナリスト視点」という見出し・独立した段落(2026-11 の振り返りで 19 本中 14 本が同じ見出しになり、テンプレとして読まれた)
- ❌「〜と同じ構造をしている」「〜と相似だ」で締めるたとえ
- ❌「データアナリストとして〜」を強調する露骨な自己紹介
- ❌ 実勤務先・受託先などの固有業務コンテクストを出すこと(該当する固有名詞は `business-profile/policies/disclosure-rules.md`)

#### B. ハマった点 / 思考プロセス(必須)

**目的**: AI 記事の「綺麗にまとまっている」を脱却する。

実装中に試行錯誤した点、最初に試した方法と最終的な方法の違い、なぜそれを選んだか
を 1〜2 か所に入れる。「失敗談」「ハマった点」と書くのではなく、自然に文章に織り込む。

例(自然):

> 最初は `PreToolUse` の matcher を `*` で全ツール対象にしていたが、SessionStart まで
> 巻き込まれてログが汚れたので `Edit|Write|Bash` に絞った。

例(不自然):

> 【ハマった点】matcher の指定で困りました。最初は `*` でしたが、これは全ツールが対象に
> なるため不適切でした。

上の「自然」の例も、形だけ真似ると型になる。2026-11 の振り返りでは「最初は〜していたが、
〜に変えた」という同じ形の文が 19 本中 16 本にあった。書き出しの形は毎回変え、実際の
エラー文・数値・ログなど、その回にしかない根拠を添える。

#### C. 全体像の図(必須)

**目的**: 読者が最初に全体をつかめるようにする。

- 冒頭から最初の見出しまでの間に、全体像の図を 1 枚置く(構成図・処理の流れ・状態遷移・比較表など、題材に合うもの)
- 構成・状態・分岐・比較を文章だけで説明している箇所があれば、図にできないか先に考える
- Mermaid でも画像でもよい。画像は `images/` に置く

#### D. 持ち帰れる締め(必須)

**目的**: 読後感を残す。読み終えた人が 1 つ持ち帰れるようにする。

- 最後の段落は、その記事で分かったことを 1〜2 文で言い切る(数字・手順・判断の基準のどれか)
- 成果物のリンクで記事を終えない。リンクは最後の段落より前に置く
- 「まとめ」見出しや禁止表現(冒頭のリスト)で締めない

#### E. 動くコード(必須)

**目的**: 読者が手を動かせる。

- コードは省略せず、コピペで動く完全な形で書く
- 言語指定を必ずつける(```bash:scripts/hooks/session-start.sh のように)
- 環境依存(Mac / Linux / Windows)があれば明記

### オプション要素(題材に応じて入れる)

#### 既存ツールとの比較

類似機能を持つ他ツールがある場合、簡潔に位置づけを書く。
過剰に他ツールを下げない、上げない。

#### Pros / Cons の見せ方

「良かった点」「惜しかった点」のような対比は、**やる場合は具体性で勝負する**。

- ❌「セットアップが簡単で良かった」
- ✅「`.claude/settings.json` 1 ファイルで動く。npm パッケージ等の追加依存ゼロ」

## 構成パターン(参考)

題材によって以下のパターンを使い分ける。毎記事で違うパターンを使う。

### frontmatter での明示

採用したパターンは frontmatter の `pattern` で記事内に明示する:

```yaml
pattern: "implementation"  # implementation / comparison / concept のいずれか
```

| `pattern` の値 | 対応するパターン |
|---|---|
| `implementation` | パターン 1: 実装編 |
| `comparison` | パターン 2: 比較・検証編 |
| `concept` | パターン 3: 概念解説編 |

`pattern` は Day 3 SKILL の Step 5.1 で履歴チェックに使われる(同じパターンが 3 回連続したら止めて構成を組み替える)。これら 3 値以外を採用したい場合は、空にせず `other` 等を入れて履歴チェックをすり抜けないようにする。

### パターン 1: 実装編 (`implementation`)

1. 題材固有のリード(なぜこれを作ったか)
2. 全体像の図
3. 実装ステップ(コード中心)
4. 思考プロセス(自然に織り込む)
5. 成果物リンク + スクショ
6. 持ち帰れる締め

### パターン 2: 比較・検証編 (`comparison`)

1. 何を比較するかの問題提起
2. 比較対象の整理
3. 検証手順(コード)
4. 結果と考察
5. 持ち帰れる締め(測った結果で何を決めるか)

### パターン 3: 概念解説編 (`concept`)

1. 概念の抽象的なイントロ
2. なぜそれが重要か
3. 具体例(コード)
4. 自分なりの解釈
5. 持ち帰れる締め

(これら以外でも、題材に合えば自由に構成して良い。その場合 `pattern: "other"` とする)

## 見やすさ

- **文の途中で改行しない**。Zenn は改行をそのまま改行として表示するので、エディタの幅で折り返すと文が途中で折れる(9/24 の記事で起きた)。1 段落は 1 行に書き、段落の間は空行で区切る
- 1 文は 80 字以内を目安にする。超えたら 2 文に分ける
- 1 段落は 200 字以内、3〜4 文までを目安にする
- 地の文のコード表記(バッククォート)は 1 段落 2 個までを目安にする。識別子をいくつも並べる説明は、コードブロックか表に移す
- 長いコードは本文に全部載せず、核の部分だけ載せて残りは成果物リポジトリに任せる

`scripts/article-readability-report.sh <記事ファイル>` で上の項目を数えられる。

## 文字数の目安

- 1500〜3000 字を基本とする
- 短すぎる(< 1000 字)→ 内容が薄い可能性、追記検討
- 長すぎる(> 4000 字)→ 焦点がぼけている可能性、分割または削減

- [ ] 「何を測り、その数字で何を決めたか」が判断の箇所に書かれている(「データアナリスト視点」の見出し・たとえの段落がない)
- [ ] ハマった点 / 思考プロセスが、その回にしかない根拠つきで書かれている
- [ ] 冒頭近くに全体像の図がある
- [ ] 最後の段落が持ち帰れる一言で終わっている(リンクで終わっていない)

- [ ] 文字数が 1500〜3000 字の範囲
