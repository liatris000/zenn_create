## 設計: なぜスコアリングを1回のAPI呼び出しに寄せるか

軸ごとに API を分けて呼ぶ実装と、1回にまとめる実装を比較する話を書く。
`20260827-product-eval-ai.md` の4軸スコアリングと似た設計判断だが、今回は
「クリエイティブの評価軸」×「予算配分ロジック」という別の切り口になる想定。

## アーキテクチャ

Mermaid で全体構成を図示する(入力: クリエイティブ案のテキスト/メタ情報 →
Claude API 構造化出力 → スコア → 予算再配分ロジック → レポート出力)。

## Step 1: 評価軸の設計

クリエイティブを何軸で評価するか(訴求の明確さ・ターゲット適合・目新しさ等、
架空の実データではなく合成データで検証する前提)を定義する。Day 2 で実装しながら軸を確定する。

## Step 2: 構造化出力での判定

Claude API の `tools` / JSON Schema でスコアの型を強制する実装。
評価軸ごとの `description` の書き方でスコアの質が変わった点を、実装しながら記録する。

## Step 3: 予算再配分ロジック

スコアから配分比率を導く単純なロジック(合成データでの検証)。
実データではなくダミーの配信結果データセットを使うことを明記する。

## 思考プロセス

実装中に詰まった点・最初に試して捨てたアプローチを Day 2 で自然な文章として書く。
