## リード文(案)

ブレークポイントは点だが、実際の画面幅は連続している。375 / 768 / 1280 の3点で確認しても、そのあいだの850pxが保証されるわけではない。この「点と点のあいだ」を機械に歩かせて、崩れ始める幅を特定する。

## 想定構成

### 1. 問題設定

- レスポンシブ対応の確認は、決めたブレークポイント上でしか行われないことが多い
- ビジュアルリグレッションテスト(VRT)も同じで、固定ビューポートのスクリーンショット比較が前提
- 一方、崩れは 642px や 911px のような半端な幅で始まる
- 既存の回避策として案内されているのは「ビューポートを少しずつ広げて、崩れ始める箇所を目で探す」という手作業
- 手作業の手順が明文化されているということは、自動化の対象がはっきりしているということ

### 2. ざっくりとしたアーキテクチャ

- 入力: 対象 URL と、掃引する幅の範囲(例: 320〜1440)
- 掃引: 幅を一定の刻みで変えながらページを評価する
- 判定: スクリーンショットの差分ではなく、**崩れの兆候をDOM・レイアウトの計測値から機械的に判定する**
  - 横スクロールが発生した(`documentElement.scrollWidth > clientWidth`)
  - 要素が親のボックスからはみ出した
  - 本来並ばないはずの要素が重なった
- 出力: 崩れ始めた幅(境界)と、そのときの要素
- Mermaid 図で 掃引 → 判定 → 境界の特定 → レポート の流れを示す予定

> スクショ比較にしない理由も書く。ベースラインが要るうえ、「崩れているかどうか」ではなく
> 「前と違うかどうか」しか分からないため、初回の掃引では答えが出ない

### 3. 実装ステップ(Day 2 で具体化)

- Playwright で幅を変えながら評価する基本形
- 刻み幅の決め方(全幅を1pxずつ見ると遅い。粗く掃いてから境界を二分探索で詰める)
- 崩れの判定条件をどこまで機械化できるか。誤検知(意図的なはみ出し)の扱い
- レポートの形。「1280は OK、850で崩れる」ではなく「崩れ始めるのは 851px」まで出す
- GitHub Pages に、わざと中間幅で崩れるサンプルページを置いて対象にする

### 4. 思考プロセス(自然に織り込む、Day 2 で追記)

- 最初はスクリーンショットの差分で判定しようとして、ベースラインが無い初回では何も言えないことに気づいた経緯
- 刻みを細かくすると実行時間が伸びる。どこで妥協したか、または二分探索でどう回避したか

### 5. データアナリスト視点(必須、2〜3 文)

- 「3点で確認した」は、連続量を3標本で代表させているということ。標本の取り方を決めずに「確認済み」と言うと、点と点のあいだの挙動を暗黙に外挿していることになる
- 掃引して境界を出すと、外挿していた区間が実測値に変わる。詳細は Day 2 で実装しながら詰める
