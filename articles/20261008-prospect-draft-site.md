## リード文(案)

初めて連絡を取る相手に「うちで作るとこうなります」を見せられないまま話を始めるのは、思っている以上にコストが高い。公開情報しかない段階で、どこまでAIに叩き台を作らせられるかを試した記録。

## 想定構成

### 1. 問題設定

- 相手が誰かは分かっていても、中身(サイト構成・文章・写真の使い方)は会ってみないと分からない
- 「会ってから作る」を「会う前に叩き台を見せる」に変えると、最初の話の解像度が上がる
- ただし人手で叩き台を作るのは工数が見合わない

### 2. ざっくりとしたアーキテクチャ

- 入力: 公開されている情報のみ(業種・地域・既存の一次情報等)
- 生成: Claude にセクション構成・文章・簡易レイアウトを組ませて 1 枚のドラフトサイト(静的 HTML)を出す
- 出力: そのまま送るのではなく、人が見て手直しする前提の「叩き台」として扱う
- Mermaid 図で入力→生成→人の確認→提示、の流れを示す予定

### 3. 実装ステップ(Day 2 で具体化)

- 公開情報の集め方(どこまでを入力にするか、個人情報や非公開情報は入れない設計)
- プロンプト設計(構成案 → 文章 → HTML の 3 段階に分けるか、一括で出すか)
- 生成物を「即送信できる完成品」ではなく「たたき台」に留めるためのガード(見出しにドラフト表記を入れる、実データではなく仮の情報は明示する 等)
- 静的サイトとして手元で確認できる形に落とす

### 4. 思考プロセス(自然に織り込む、Day 2 で追記)

- 最初は本文の文章まで一気に生成しようとしたが、構成が決まる前に文章を書かせると手直しの範囲が大きくなりすぎた点をどう解決したか
- 「公開情報だけ」で品質をどこまで担保できるかの境界

### 5. データアナリスト視点(必須、2〜3 文)

- 「何が決め手で構成を選んだか」を後から追えるようにしておくと、次に似た相手向けに叩き台を作るときの再現性が上がる。これは分析の意思決定ログを残す発想と同じ
- 詳細は Day 2 で実装しながら詰める

### 6. 成果物リンク + スクショ

- Day 3 で GitHub Pages にデプロイしたサンプルのリンクとスクリーンショットを追加

## 実装方針メモ(PR用)

- 技術スタック: Claude Code / Claude API + 静的 HTML(フレームワーク無し、または軽量な静的サイトジェネレータ)
- GitHub Pages で公開可能(静的サイトのみのため)
- 想定実装規模: M(1〜2日)
