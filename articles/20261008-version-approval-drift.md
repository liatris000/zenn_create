## リード文(案)

同じ対象を何度も作り直せるようになると、新しい困りごとが増える。「今出ているものが、最後に人が確認したものと同じかどうか」が、パッと見では分からなくなる。

## 想定構成(パターン: 概念解説編)

### 1. 概念の抽象的なイントロ

- 「最新版」と「確認・承認された版」は、そもそも別の軸である
- AIが何度でも再生成できるようになったことで、この2つがズレたまま気づかれないケースが増えている
- 具体例として GitHub の「Require approval of the most recent reviewable push」設定 — 新しいコミットが積まれると承認が自動でリセットされ、見た目には承認済みに見えても実際は未承認、というギャップが実際に起きている

### 2. なぜそれが重要か

- 「壊れているかどうか」ではなく「壊れていることに気づけるかどうか」が問題
- 人が最後に見たのはどの版か、を追跡する仕組みがないと、古い確認結果を新しい版にそのまま適用してしまう
- AIで生成物を反復更新するワークフローほど、この分離を意識的に設計する必要がある

### 3. 具体例(コード、Day 2 で書く)

- 生成物にバージョンID(内容のハッシュ等)を付与する
- 「人が確認した版のID」を別に保持し、最新版のIDと突き合わせて一致しなければ「未確認」を明示する
- 突き合わせのロジックと、簡単な確認 UI or CLI 出力のサンプル

### 4. 自分なりの解釈(思考プロセスを自然に織り込む、Day 2 で追記)

- 最初は「最新かどうか」だけを見るチェックを書いていたが、それでは「更新されたのに未確認」を検知できないことに気づいた経緯
- 「最新」と「確認済み」を同じ変数で扱っていたところを分離した理由

### 5. データアナリスト視点(必須、2〜3 文)

- 分析基盤でも「最新のデータ」と「レビュー済みの集計ロジック」がズレたまま運用されることがある。データの鮮度と、ロジックの検証済み状態は別々に管理する必要がある、という発想と同じ構造
