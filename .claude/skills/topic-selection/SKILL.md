# 題材選定 skill

AI 記事の題材選定を業務プロフィールベースで行うための判断ロジック。
詳細仕様は `business-profile/companies/personal/ai-articles/topic-selection.md` を参照。

## 判断フロー(7 ステップ)

```
[業務プール] → ① 公開可否 → ② キャッチアップ価値 → ③ 需要シグナル
              → ④ 供給シグナル → ⑤ スイートスポット判定
              → ⑥ Liatris 確認 → ⑦ 採用
```

詳細は `business-profile/companies/personal/ai-articles/topic-selection.md` を直接参照する。

④ と ⑤ のあいだに、このリポジトリ側で 2 つのゲートを挟む
(下記「採用前の 2 つのゲート」)。③④ の測り方の規則は「需要と供給の語のずれ方を見る」を参照。

## 発動タイミング

- Day 1 Routine 起動時(必ず)
- Liatris から「題材を考え直したい」と指示された時
- 候補題材が公開可否ルールに抵触するか確認したい時

## 重要: ルーティン完走前提

このスキルは Day 1 ルーティンから呼ばれるため、**Liatris の対話確認待ちで停止してはならない**。判定結果に基づいて自動採用または自動中止のどちらかに必ず分岐する。詳細は下記「自動採用ロジック」セクション参照。

## 前提 ⚠️ 必須

> **`business-profile/` submodule が登録済みかつ同期済みであること。**
> このスキルは `business-profile/` 配下のファイル(README、`disclosure-rules.md`、`topic-selection.md` 等)を読み込んで判断する設計になっており、**submodule なしでは判断フローを 1 ステップも実行できない**。
>
> 確認方法:
>
> ```bash
> test -f ~/zenn_create/.gitmodules \
>   && test -f ~/zenn_create/business-profile/policies/disclosure-rules.md \
>   && echo OK || echo "NG: submodule 未登録 or 未同期"
> ```
>
> NG の場合はこのスキルの判断フローを開始してはいけない。**Day 1 skill (`day1-kickoff`) 側の Step 1.5 で Liatris に submodule 登録を依頼して中止する**運用になっている。間違ってもダミー候補や記憶ベースで題材を提案しないこと。

その他:

- SessionStart hook (`scripts/session-start.sh`) で submodule が `--remote --merge` 同期済み
- Liatris が同じセッション内にいて、確認を返せる状態

## 業務プール参照の手順

1. 業務プールの README を順に view する。**対象は固定リストで持たず、実行時に列挙する**
   (このリポジトリは Public なのでプール名をここに書かない。プールの増減にも自動で追随する):

   ```bash
   find business-profile/companies -mindepth 2 -maxdepth 3 -name README.md | sort
   ```

   どのプールを対象にするかの正本は `business-profile/companies/personal/ai-articles/topic-selection.md`。

2. 各種のメタデータをチェック:
   - `status: 未着手` のものだけを候補にする
   - `disclosure: blocked` は除外する
   - `catchup_value: high` を優先する

3. **本業(実勤務先)領域は対象外**(business-profile 側の `topic-selection.md` で明記されている)
   - 該当領域の題材候補が思い浮かんでも、Liatris に必ず確認する
   - どの領域が該当するかは `business-profile/policies/disclosure-rules.md` を見る

## 既存記事に引きずられない

`articles/` 内の既存記事を確認するのは「題材被り防止」のためであり、「既存記事の延長線上の題材を選ぶ」ためではない。

### NG パターン

- 既存記事が「Claude Code Hooks」を扱っている → 新記事を「Claude Code の `.claude/` 整備」のような連続性のある題材にする
- 既存記事が「Firecrawl」を扱っている → 新記事も MCP 系で揃える

### 正しい挙動

業務プールから独立に判定する。既存記事との連続性は採用基準に含めない。

業務プールから候補を選んだ後、`articles/*.md` をスキャンして「題材として被っていないか」だけチェックする(被っていれば不採用、それ以外は採用)。

## 業務プール外題材の扱い

業務プールに採用可能な ★★★/★★ 候補がある限り、業務プール外を選んではいけない。

業務プール外を採用してもよい条件:

1. 業務プールから ★/△ または候補ゼロしか出ない
2. 業務プール外候補が AI 駆動開発・Claude Code 運用・MCP・スキル設計等、Liatris の AI 駆動開発キャリア軸に直接関わる題材である

この条件を満たす場合のみ、業務プール外候補を採用候補として PR 本文の「候補リスト」に含める。

業務プール外候補の判定は、業務プール内候補と同じ需要×供給シグナルロジックで行う。

## 公開可否チェックの手順

1. `business-profile/policies/disclosure-rules.md` を view する
2. 候補題材に該当する会社・プロジェクトのセクションを確認
3. 「❌ NG」の項目に抵触しないか 1 つずつチェック
4. 抵触の可能性があれば候補から除外、または Liatris に確認

## 需要と供給の語のずれ方を見る ⚠️ 必須

③ 需要シグナルと ④ 供給シグナルで実際に使った検索語を、それぞれ 1 行で記録し、
PR 本文の「採用判定の根拠」に併記する。そのうえで、④ の語が ③ の語から
**どうずれているか**を見る。

| ④ の語のずれ方 | 例 | 扱い |
|---|---|---|
| **手法・技術の限定**を足した | ③「中間の画面幅で表示が崩れる」→ ④「それを自動で検出する」 | OK。③ の需要判定をそのまま使う |
| **問題そのものを別の問題に置き換えた** | ③「提案書の自動生成」→ ④「初回接触前に相手ごとの叩き台サイトを用意する」 | **NG**。③ の判定を持ち越さない。④ が扱う問題でゲートA をやり直す |

> 前者は「皆が持っている問題 P に、まだ書かれていない手法 T で答える」形。これは良い題材なので殺さない。
> 後者は、**需要を測った問題と、記事が実際に扱う問題が別物**になっている。
> これを許すと、どんな切り口でも「需要 mid × 供給 空白 = ★★」を作れてしまい、
> **切り口を狭めるほど採用されやすくなる**。
>
> 2026-09-14 の PR #84 が後者。需要は「提案書自動生成 / AI 叩き台生成」で測り、
> 記事が扱う問題は「公開情報のみを入力に、相手ごとの叩き台サイトを事前に用意する」だった。
> 後者はゲートA を通らないので、正しくは 需要 low × 供給 空白 = △(自動採用しない)。

### 罠4: 供給空白の読み違え

(罠1〜3 は `business-profile/companies/personal/ai-articles/topic-selection.md` の
③ 需要シグナル側にある。罠4 は ④ 供給シグナル側の罠。)

供給が空白なのは「まだ誰も書いていない」とは限らない。
**「そもそも誰もやらないので書く対象が無い」**の可能性を先に潰す。

見分け方はゲートA。④ が扱う問題でゲートA を通らなければ後者。
読者がその問題設定を共有していないので、記事にしても「何を伝えたいか分からない」になる。

## 採用前の 2 つのゲート ⚠️ 必須

⑤ スイートスポット判定に入れる前に、候補ごとに次の 2 つを通す。
どちらかで落ちた候補は判定を付けずに**候補から外し、次候補へ進む**。

**どちらも「自分で読者の気持ちを想像して判定」してはいけない。**
自動実行で自己判定させると必ず「通過」になる。下の手順の通り、外形で判定する。

### ゲートA: 読者がその問題を持っているか

1. 題材の問題設定を、**業務文脈を一切足さずに** 1 文で書く
2. その 1 文と同じ困りごとを述べている**実在の投稿・記事・Issue を 3 件**挙げる
3. **各ページから、その困りごとを述べている文を 1 文ずつ引用する**

| 3 件すべてに引用文を付けられたか | 判定 |
|---|---|
| 付けられた | 通過。その 1 文が ③ の検索語になる |
| 付けられない(URL は出るが、引用できるのはページの話題だけ) | **需要 low**。候補から外す |

> **引用できないものは数えない。** 検索すれば隣接した話題のページは必ず出てくるので、
> URL の件数だけで判定するとゲートが効かない。
>
> 実測(2026-09-14): #84 の問題設定で検索すると営業の事前準備の記事が 7 件出るが、
> 「初回接触前に相手のサイトの叩き台を用意するコストが高い」と**書いてあるページは 1 件も無い**。
> 一方「中間の画面幅で表示が崩れる」は、`768px 付近は特に崩れやすい` と
> **書いてあるページが複数ある**。話題が近いことと、同じ困りごとが書かれていることは別。
>
> 「たぶん困っている人はいるはず」で通してはいけない。引用文が挙がらないこと自体が判定。

### ゲートB: 頼まれていない相手に向けた成果物が中心にないか

題材の中心が、**依頼していない第三者**(見込み客・未連絡の相手・取引先候補)に向けて
成果物を作る / 届ける行為になっているか。

| | 判定 |
|---|---|
| なっている | **自動採用しない**。候補から外す |
| なっていない(自分・自社・依頼済みの相手が対象、または公開情報を読むだけ) | 通過 |

> 罠1(炎上バズ)は「**既に**否定的に語られている題材」を弾く。
> ゲートB は「まだ誰も語っていないが、公に勧めると否定的に受け取られる行為」を弾く。
> 供給が空白なのは、その行為を公に勧める人がいないからかもしれない(罠4 と対)。

## 自動採用ロジック

判定が出たら、以下のロジックで自動採用または中止判断する。**Liatris 確認待ちで停止しない**(ルーティンを完走させるため)。

### 採用ルール

| 候補のうち最高判定 | 挙動 |
|---|---|
| ★★★ が 1 つ以上 | **第1候補(★★★)を自動採用**。Day 1 を続行。 |
| ★★ が 1 つ以上、★★★ なし | 次の 2 つを**両方**満たす場合に限り、第1候補(★★)を自動採用。<br>(a) ④ の語のずれ方が**手法・技術の限定**であること(問題の置き換えでないこと)<br>(b) ③ の語が**ゲートA を通過**していること<br>満たす場合は Day 1 を続行し、PR 本文に「自動採用された ★★ 候補のため、題材として弱い可能性あり」と注意書きを記載。<br>**満たさなければ自動採用しない**(候補から外して次候補へ。次候補が無ければ Day 1 を中止)。 |
| ★ または △ のみ、または候補ゼロ | **Day 1 を中止**。Chatwork に「今週は中止: 採用可能な候補がありません」と通知。 |

### 候補は打ち切らずに全部判定する

★★ が見つかっても、**そこで残りの候補の判定を省略しない**。
採用ルールは「候補のうち**最高**判定」を採る形なので、全候補を判定し終えるまで
最高判定は確定しない。

PR 本文の候補リストに「未検証(採用候補が ★★ で決まったため詳細検証は省略)」と
書かれていたら、それは打ち切った証拠。

> 実測(2026-09-14): 打ち切った結果、未検証のまま残した候補のほうが ★★★ だった。

### 自動採用時の出力

skill の出力として、以下のフォーマットを Step 6 (PR 作成) に渡す:

```
題材: [題材名]
業務プール: business-profile/companies/<X>/README.md の <種>
判定: [★★★/★★] / 需要: [high/mid/low] / 供給: [空白/部分的/飽和]
需要の検索語: [③ で実際に検索した語]
供給の検索語: [④ で実際に検索した語]
語のずれ方: [手法の限定 / 問題の置き換え](問題の置き換えなら自動採用しない)
ゲートA(読者がその問題を持っているか): 通過 / 根拠 3 件(URL + 引用文): [...]
ゲートB(頼まれていない相手が対象でないか): 通過
キャッチアップ価値: [high/mid] / 推定実装規模: [S/M/L]
公開可否: [clean/careful] / 抵触リスク: [なし/あり(careful なら Liatris レビュー必須)]
理由: [1〜2 行]

[★★ の場合のみ] 注意: 自動採用された ★★ 候補のため、題材として弱い可能性あり。Liatris レビューで判断してください。
```

### Liatris の介入ポイント

題材の最終判断は、Day 2 起動前の朝(火曜朝)の PR レビューで Liatris が行う。NG の場合は PR を close することで Day 2 が走らなくなる(Day 2 skill は `[Day 1/3 WIP]` PR を探すため)。
詳細は [`docs/cycle-overview.md`](../../../docs/cycle-overview.md) の「Liatris チェックポイント」セクション参照。

### 例外: disclosure: careful の場合

候補が `disclosure: careful` の場合、自動採用しても OK だが、PR 本文の冒頭に **「⚠️ disclosure: careful 題材につき、Liatris レビュー必須」** と明記する。

## `.claude/` 配下のファイル生成を伴う題材の扱い

題材の成果物に `.claude/mcp.json` 等、`.claude/` 配下のファイル生成が含まれる場合は、以下を必ず守る:

- 採用判定自体は通常通り(★★★/★★ 判定でブロックしない)
- ただし PR 本文の実装方針セクションに **「成果物に `.claude/` 配下のファイル含む → publish-artifact.sh の `_claude_template/` 機構を使う」** と明記すること
- Day 2 skill の Step 3 で `_claude_template/` への配置が指示されているため、それに従う

これにより、Claude Code の `.claude/` 書き込み保護と Routine 自動化が両立する。

## 候補リスト公開(必須)

採用判定の前に、検討した候補すべてを列挙して PR 本文に記載する。これにより Liatris レビュー時に「なぜこれが選ばれたか」「他にどんな候補があったか」が分かるようになる。

採用判定を出す前に、以下のフォーマットで候補一覧を整理しておく(Step 6 の PR 本文で使う):

```
## 候補リスト

業務プールから:
- [候補1] (業務プール: <X>) → 判定: ★★★ → 採用
- [候補2] (業務プール: <Y>) → 判定: ★★ → 不採用 (理由: <なぜ第1候補に劣るか>)
- [候補3] (業務プール: <Z>) → 判定: ★ → 不採用 (理由: 採用基準未達)
- [候補4] (業務プール: <W>) → ゲートA 落ち → 不採用 (理由: 同じ困りごとの実在言及が 0〜2 件)

業務プール外から(検討した場合のみ):
- [候補A] (テーマ: <概念領域>) → 判定: ★★ → 不採用 (理由: 業務プール内に上位候補あり)
```

採用候補だけでなく、検討して落ちた候補も書く。落ちた理由は 1 行で OK。

## 情報漏れ対策

このスキルを使う時、以下を厳守する:

- 題材選定の commit message に業務コンテクストを出さない
  - ❌「(実在の事業名)の OCR 自動化を題材として採用」
  - ✅「Day 1: 題材選定完了」
- PR 本文の題材説明に業務コンテクストを出さない
  - ❌「(実在の事業名)で必要な機能」
  - ✅「OCR で契約書をパースする UI」

詳細は `docs/cycle-overview.md` の「情報漏れ対策」セクション参照。
